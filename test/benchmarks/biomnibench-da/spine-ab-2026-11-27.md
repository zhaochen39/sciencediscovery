# BiomniBench-DA JiuwenSwarm Spine 对照运行手册

这次实验覆盖仓库当前固定的 45 个活跃用例。两组使用同一个 Git SHA、同一台 Linux 服务器、同一个 JiuwenSwarm 后端、同一份数据和官方评分标准。生成模型与评分模型各自固定，推理设置均为 `enabled/low`。每组串行执行，避免同机两组抢占 CPU、内存和模型配额。

| 组 | 开关 | 适用范围 |
|---|---|---|
| A，`off` | 关闭 Scope Projection 和 Scope 观察 | 同版本 JiuwenSwarm 基线 |
| B，`on` | 开启 Scope Projection 和 Scope 观察 | 验证这组开关在标准任务中的命中与代价 |

Scope 折叠和显式 Scope 管理保持关闭。标准用例在新会话提交初始 Run，没有提交 `researchResume`。检查点恢复、节点记忆等显式入口继续用专项验收覆盖。观察到 Scope 记录后，仍需查实际 Projection 命中才能判断历史是否压缩。一次任务可以包含多次模型请求，历史 Projection 有机会在符合条件的后续 Run 命中。

## 准备

从个人仓 `feat/research-spine` 获取此次验收提交，固定 SHA 后准备同一份 Linux checkout。准备 Node、pnpm、uv、Playwright Chromium，以及 `.ci/research-requirements.txt` 所需的 Python 环境。先用所选 checkout 执行一次已有的构建和浏览器安装流程。服务器需要可用的 JiuwenSwarm 与 bubblewrap。若主机缺 Chromium 系统库，先按服务器现有 CI 的方式安装。

运行盘默认至少保留 64 GiB 和 150,000 个空闲 inode。报告盘至少保留 5 GiB 和 10,000 个 inode。数据集全量清单约 83 GB，按缓存现状另预留空间。`data` 可指向已有的已授权缓存，两组每次尝试各自创建临时工作区。若缓存有缺失，需要环境中的授权 `HF_TOKEN` 才能下载。

```bash
# 在已固定提交的仓库根目录执行。
source /path/to/approved-model-env.sh
export CI_ALLOW_REAL=1
export UV_CACHE_DIR=/srv/science-ab/cache/uv
export TMPDIR=/srv/science-ab/tmp
mkdir -p "$TMPDIR"
export SCIENCE_AGENT_PORT=14410
export SCIENCE_AGENT_RUNNER_PORT=14411
export SCIENCE_AGENT_LEGACY_PORT=14510
export SCIENCE_AGENT_MEMORY_GRAPH_PORT=17784

# 先确认上面的本机端口空闲。若服务器已有该服务，选择同组空闲端口。
bench=test/benchmarks/biomnibench-da
output=/srv/science-ab/results-2026-11-27
runtime=/srv/science-ab/runtime-2026-11-27
data=/srv/science-ab/pinned-biomni-data
prepare_results=/srv/science-ab/prepare-2026-11-27
bench_python=/srv/science-ab/benchmark-venv/bin/python

# 已按同一 SHA 准备过时可跳过安装步骤。
node test/support/tagged/shared.mjs prepare --profile release --slice e2e-real \
  --backend jiuwenswarm --output "$prepare_results"
uv venv --python 3.14 /srv/science-ab/benchmark-venv
uv pip install --python "$bench_python" --only-binary :all: -r .ci/research-requirements.txt

run_arm() {
  local arm="$1"
  shift
  "$bench_python" "$bench/suite.py" --backend jiuwenswarm --spine-arm "$arm" \
    --results "$output/$arm" --runtime "$runtime/$arm" --data-root "$data" \
    --python "$bench_python" "$@"
}

run_arm off --preflight-only
run_arm on --preflight-only
```

`E2E_LLM_BASE_URL`、`E2E_LLM_MODEL`、`E2E_LLM_TOKEN` 用于生成。`BIOMNI_JUDGE_BASE_URL`、`BIOMNI_JUDGE_MODEL`、`BIOMNI_JUDGE_API_KEY` 用于评分。驱动会设置 tagged runner 所需的评分变量。预检冻结 45 例清单、开关、提交、模型、运行预算和磁盘阈值。第一次正式运行的日志用于确认服务启动、模型可达和数据可读。标准驱动保留失败和重试，恢复时沿用相同运行目录和命令。

## 正式执行

```bash
run_arm off
run_arm on

"$bench_python" "$bench/compare_spine.py" --off "$output/off" --on "$output/on" \
  --output "$output/comparison"
```

建议保留启动顺序及时间窗口。两组都应执行，即使 A 组返回非零也要先保存证据，再判断环境问题是否会影响 B 组。若用 `set -e` 包装命令，显式记录每组退出码，确保第一组非零时仍能检查和启动第二组。测试期间若发现明显的环境故障，先修复并记录原因，正式 A/B 用新目录重新固定配置。

## 验收结果

先核对两组 45 例完成数、`biomni-gate.json`、未解决用例和官方评分。再比较同病例的生成输入、输出与总 Token，评审 Token、模型请求数、工具调用与轮次、Shell 次数、耗时和峰值 RSS。比较文件包含每项指标的有效配对数、均值变化、配对差值中位数和逐例差值。出现持续接近两倍的耗时差时，再查相应用例的供方重试、首包、轮次和工具执行时间。

- `off|on/spine-arm.json` 记录组配置。
- `off|on/status.jsonl`、`summary.json` 和 `tracking-required.json` 记录首跑、重试及未解决项。
- `off|on/attempt-costs.json` 记录全部尝试的已知 Token 成本及用量缺失次数。配对总 Token 只统计用量完整的病例。
- `off|on/cases/<case>/<attempt>/` 留存运行日志、评分和执行证据。`stack.log` 中的 `scope.projection.applied` 提供实际命中。
- `comparison/comparison.json` 汇总指标，`comparison/cases.csv` 提供逐例明细。命中分为所有尝试与最终评分使用的生成尝试两个口径。缺少运行日志时，该病例的最终命中保留为空。

首要条件是两组都完成评分且结果正确。比较平均分和逐例明显降分，定位质量波动，再解释成本。若开启组实际命中为零，报告应明确写出覆盖结果，汇总数据可以衡量开启后的行为及额外开销。历史压缩的效果由实际命中的任务或独立长历史用例提供证据。
